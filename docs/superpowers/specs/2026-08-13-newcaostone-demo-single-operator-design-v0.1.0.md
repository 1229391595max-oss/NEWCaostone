## 1. 文档目的

本设计将 NEWCaostone 的当前产品范围、用户模式、数据生命周期、AI 使用方式、部署边界和验收标准固化为一个可审阅版本，作为后续实施计划的依据。

本版本只定义设计，不代表功能已完成、已部署或已通过 Azure 验收。用户批准本文档后，再拆分实施计划、算法规格和交付批次。

## 2. 核心结论

NEWCaostone 采用一个代码库、一个可部署应用、一个单一操作者账户和一个匿名观众 Demo 模式：

- 操作者继续使用现有 BP 的表格导入、识别、字段映射、标准化、质量检查、原子提交和版本库流程。
- 观众不注册、不上传、不修改数据，只读取操作者发布的预设演示数据。
- 每位观众拥有独立的临时 Demo 会话，可使用 AI 对话并模拟行动卡操作，但不会改变公共数据，也不会产生真实平台任务。
- PostgreSQL 是持久状态的权威来源；Azure Blob 保存标准化数据集、分析产物和导出物。
- 不建设真实客户多账户、团队、邀请、租户计费或完整客户级 RLS。
- AI 使用操作者提供的单一临时 API Key，固定调用低消耗模型，并由服务器执行证据约束。
- 首发不直接修改 Shopee、UpSeller 或广告平台，也不自动下采购单。

## 3. 产品目标与非目标

### 3.1 目标

1. 保留并选择性复用现有 BP 已实现且经过验证的导入和数据版本流程。
2. 提供可公开访问、无需观众注册的分析演示。
3. 展示新品预测、确定性利润归因、证据约束 AI 问答和完整行动卡闭环。
4. 让操作者可长期保留标准化后的演示数据版本，并手动选择公开 Demo 使用的版本。
5. 在不承担真实客户系统复杂度的前提下，达到稳定、可重复、可恢复的 Demo 验收标准。

### 3.2 非目标

本次明确不建设：

- 真实客户或真实销售数据处理；
- 多客户、多租户、团队、邀请、成员和角色系统；
- 面向真实客户的 Production 安全与合规体系；
- 老品年度预测；
- 独立竞品预测平台；
- 自动采集竞品数据；
- 跨平台异常诊断；
- 直接修改店铺广告；
- 自动向 Shopee、UpSeller 或广告平台写入；
- 自动生成并提交真实采购单；
- 真实 BP 数据迁移；
- 双环境 Staging/Production 晋级体系、定制域名或完整灾难恢复工程。

## 4. 用户模式与权限

### 4.1 观众 Demo 模式

观众通过 Azure 公开 HTTPS URL 直接进入 Demo，不需要注册或登录。

观众可以：

- 查看操作者已发布的预设数据和分析页面；
- 使用系统提供的推荐问题；
- 输入有限长度的自由文本，与 AI 连续对话；
- 在临时会话中模拟批准、调整或驳回行动卡；
- 查看模拟操作后的会话内结果。

观众不可以：

- 上传 Excel、CSV 或其他文件；
- 新建、删除、编辑或发布数据版本；
- 修改公共预设数据；
- 查看其他观众的 AI 对话或行动状态；
- 产生真实采购、广告或平台操作；
- 获得操作者功能或后台入口。

### 4.2 观众会话生命周期

每位观众获得一个服务端生成的不可预测会话标识。该标识通过安全 Cookie 与浏览器关联，不能由前端自行指定数据范围。

- 刷新、前进或后退：继续当前会话，不算退出。
- 关闭标签页：不立即删除会话，重新打开时可在有效期内继续。
- 空闲超时：默认 30 分钟。
- 绝对有效期：默认 2 小时。
- 主动点击“结束 Demo”：立即清理该会话的 AI 对话、摘要和模拟行动卡状态。
- 清除 Cookie、换浏览器或重新开始 Demo：建立新会话。
- 应用重启：未过期会话应从 PostgreSQL 恢复，不因进程重启丢失。
- 到期会话：后台按计划清理；再次访问时引导建立新会话。

会话仅保存演示所需状态，不为每位观众复制整套数据。

### 4.3 单一操作者模式

系统只有一个操作者账户和一个 `operator_workspace`。

操作者可以：

- 登录受保护的操作者入口；
- 上传仅含虚构、修改或脱敏数据的 Excel/CSV；
- 运行 BP 导入与标准化流程；
- 查看提交历史和标准化数据版本；
- 将某个已提交版本手动发布为新的公共 Demo 预设版本；
- 使用 AI、持久保存操作者行动卡决策并导出采购/广告任务文件；
- 查看分析、证据和结果复盘。

账户设计保持最小化：

- 不提供注册、邀请、团队、成员或角色管理；
- 操作者用户名和密码哈希由服务器部署配置提供；
- 使用安全、HttpOnly、SameSite Cookie；
- 不建设找回密码页面；需要重置时更改部署配置；
- 所有操作者路由和写操作均由服务器验证，不依赖前端隐藏按钮。

## 5. 数据导入与长期保留

### 5.1 保留当前 BP 流程

NEWCaostone 继续采用当前 BP 数据流程：

```text
上传文件
  → 识别报表类型
  → 字段映射
  → 标准化
  → 数据质量检查
  → 多文件原子提交
  → 生成可长期保留的标准化数据版本
  → 分析、证据、AI 与导出
```

选择性复用范围包括现有 BP 的报表适配器、标准化规则、原子提交逻辑、数据版本库、PostgreSQL/Alembic/Blob 接口、服务层和相关测试。迁移时以当前代码和测试证据为准，不因历史文档存在就假设功能可用。

### 5.2 原始文件与标准化数据

原始 Excel/CSV 只作为临时处理输入：

- 上传成功后进入有界临时区；
- 完成提交、排除、失败、取消或超时后删除；
- 不把原始表格作为长期业务数据库；
- 不允许原始内容出现在日志、公开错误信息或 AI 请求中。

长期保留的对象是：

- 标准化后的数据集版本；
- 数据质量结果和提交元数据；
- 确定性分析结果；
- 可追溯证据引用；
- 操作者行动卡决策；
- 导出文件和结果复盘记录。

因此，“把上传数据合并成一个长久保留的数据库”在本设计中的准确含义是：将通过检查的多份输入原子合并为结构统一、可追踪、可版本化的标准化数据，而不是永久保存每个原始文件。

### 5.3 原子性、重复导入与失败处理

- 同一批多文件要么全部提交成功，要么全部回滚，不产生半成品版本。
- 每次提交生成唯一批次标识和数据版本标识。
- 重放同一已确认批次必须幂等，不重复累计数据。
- 检测疑似重复上传并要求操作者确认或阻止重复提交。
- 不支持的格式、缺失必填字段或质量检查失败时，提供可理解的错误摘要。
- 失败消息不暴露服务器路径、连接字符串、API Key 或供应商原始响应。

## 6. 公共预设数据发布

操作者从已经成功提交的数据版本中，手动选择一个版本发布为公共 Demo 预设。

发布规则：

1. 只有状态完整且通过最低质量检查的版本可以发布。
2. 发布操作只修改“当前公共版本”指针，不复制整套数据。
3. 新观众会话读取最新已发布版本。
4. 已经开始的观众会话固定使用进入时的数据版本，直到会话结束或过期。
5. 操作者发布新版本不会改变正在演示的观众页面、AI 证据或行动卡上下文。
6. 发布失败时保留原公共版本，不出现无数据状态。
7. 可回退到先前已提交且仍有效的演示版本。

## 7. 数据与部署架构

### 7.1 逻辑组件

```text
Azure 公开 HTTPS URL
        │
        ├── 匿名观众 Demo 路由
        │      ├── 只读分析
        │      ├── AI 对话
        │      └── 临时行动卡模拟
        │
        └── 单一操作者受保护路由
               ├── BP 表格导入与提交
               ├── 数据版本库与发布
               ├── 持久行动卡
               └── 任务文件导出

应用服务
  ├── PostgreSQL：权威关系数据、版本、会话、状态
  ├── Azure Blob：标准化数据集、分析产物、导出物、临时上传区
  └── OpenAI API：证据约束的解释和问答
```

### 7.2 PostgreSQL

PostgreSQL 是持久状态的权威来源，使用 Alembic 管理数据库迁移。核心逻辑实体包括：

- `operator_workspace`：唯一操作者工作区；
- `import_batches`：导入批次及状态；
- `dataset_versions`：标准化数据版本；
- `published_demo_version`：当前公共版本指针；
- 标准化事实表和维度表；
- `demo_sessions`：匿名会话、固定数据版本和过期时间；
- `ai_conversations` / `ai_messages`：限定范围的会话对话；
- `action_cards` / `action_decisions`：建议和决策状态；
- `analysis_artifacts` / `exports`：分析与导出元数据。

实体名称可在实施计划中按现有 BP schema 对齐，但必须保留上述职责分离。

### 7.3 Azure Blob

一个 Blob Storage 账户和受控容器即可满足本次合成数据 Demo。对象按用途区分：

- 临时上传区：设置短生命周期，提交或失败后删除；
- 标准化数据集区：按数据版本不可变保存；
- 分析与证据区：保存可追踪产物；
- 导出区：保存有期限的采购/广告任务文件。

Blob 元数据和数据库版本必须相互引用。数据库提交失败时不能留下被视为已发布的孤立对象。

### 7.4 隔离方式

本次不建设完整客户多租户和客户级 RLS。隔离依靠：

- 一个固定 `operator_workspace`；
- 服务器从已验证 Cookie 解析观众会话，禁止客户端传入任意 session scope；
- 所有公共数据查询绑定会话固定的 `dataset_version_id`；
- 所有 AI 消息和模拟行动绑定当前 `demo_session_id`；
- 操作者写路由使用独立的服务端认证守卫；
- 公共接口不提供通用数据写入能力。

这是 Demo 简化方案，不应被描述为适合真实客户的租户安全模型。

## 8. 分析、预测与利润归因

### 8.1 确定性计算优先

销量、库存、广告、成本、利润和预测的数值先由可测试的确定性代码计算。AI 不负责生成权威数字，也不能覆盖确定性结果。

系统保留以下产品能力：

- 现有 BP 的数据导入、标准化和分析能力；
- 新品预测；
- 确定性利润归因；
- 证据约束 AI 问答；
- 完整行动卡和结果复盘。

### 8.2 算法规格边界

本 `v0.1.0` 是产品范围与系统架构设计，不虚构尚未确认的业务公式。以下内容必须在对应开发批次开始前形成独立、可审阅的算法子规格：

- 新品预测的输入字段、冷启动方法、时间窗、输出区间和回测指标；
- 利润归因的收入、平台费、广告费、商品成本、物流、税费、退款和汇率口径；
- 缺失数据、异常值和币种转换规则；
- 置信度的计算方法；
- 行动建议触发阈值和结果复盘周期。

在算法子规格批准前，可以迁移已有确定性能力和搭建接口，但不得将临时公式包装为最终业务逻辑。

### 8.3 图表原则

分析页面采用多图表分析仪表盘风格，图表只服务于比较、趋势、构成、预测和证据定位。销售/广告、库存、利润和预测页面可以使用图表；登录、上传和配置页面不添加装饰性图片。

## 9. AI 设计

### 9.1 模型与 API Key

- 全应用使用操作者提供的一个临时 OpenAI API Key。
- 固定模型：`gpt-5.4-mini-2026-03-17`。
- 推理强度：`reasoning.effort: low`。
- API Key 仅保存在服务器环境变量或 Azure App Service 应用设置中。
- API Key 不进入浏览器、前端 JavaScript、Git、数据库、日志或导出文件。
- 演示结束后撤销该 Key，并从部署配置中删除。

考虑到本次仅使用合成/脱敏数据且 Key 会在演示后删除，不建设 Azure Key Vault、Managed Identity、自动轮换或高级密钥审计。但“减少高级保护”不等于允许密钥暴露给客户端。

### 9.2 观众交互

观众可选择推荐问题，也可输入自由文本。产品界面不显示固定的单次对话次数上限，但保留以下资源边界：

- 单次输入默认最多 2,000 个字符；
- 单次输出最多 1,200 tokens；
- 每个会话同一时间只允许一个在途 AI 请求；
- 上下文仅保留最近 4 轮和安全摘要，避免无限增长；
- 全应用设置并发上限和 Azure 部署级预算上限；
- 不启用 Web Search、Code Interpreter、File Search 等额外付费工具。

这些限制控制异常消耗，不把正常演示变成“每次只能问很少内容”。实际数值可在压测后向下调整，但不能取消总并发和部署预算保护。

### 9.3 证据约束

AI 只能使用：

- 当前会话固定的标准化数据版本；
- 已完成的确定性分析；
- 行动卡中的结构化字段；
- 与结论直接关联的证据引用。

推荐回答结构为：

1. 结论；
2. 关键数字；
3. 证据来源或数据版本；
4. 置信度；
5. 不确定性和限制。

AI 不得：

- 修改标准化数据；
- 自行批准行动卡；
- 执行真实平台操作；
- 在证据不足时编造数字或原因；
- 把其他观众的对话纳入当前回答。

证据不足时应明确回答“当前数据不足以支持该结论”，并说明缺少什么。OpenAI API 不可用、达到预算上限或超时时，界面显示 AI 暂不可用；确定性分析仍可继续使用，不生成伪造的降级回答。

## 10. 行动卡设计

每张完整行动卡至少包含：

- 建议行动；
- 数字依据；
- 置信度；
- 证据引用；
- 建议影响范围；
- 批准、调整、驳回状态；
- 调整后的数量、预算或日期；
- 任务导出状态；
- 结果复盘状态和实际结果。

### 10.1 观众行为

观众可在自己的临时会话内模拟批准、调整或驳回。该操作：

- 不修改公共行动卡模板或数据；
- 不生成真实平台任务；
- 不向 Shopee、UpSeller 或广告平台发送请求；
- 不影响其他观众；
- 随会话结束或过期而清除。

### 10.2 操作者行为

操作者的行动卡决策持久保留。批准或调整后可以导出采购/广告任务文件，交由人工复核和后续执行。首发闭环以“建议 → 数字与证据 → 人工批准/调整/驳回 → 文件导出 → 结果复盘”为终点。

## 11. 最小安全基线

虽然本应用只用于合成数据 Demo，以下基线仍必须保留：

- Azure HTTPS；
- API Key 仅在服务器端；
- 单一操作者认证和受保护路由；
- 不可预测的观众会话标识；
- Cookie 使用 HttpOnly、Secure 和适当的 SameSite；
- 所有写操作使用基本 CSRF 防护；
- 文件类型、大小、字段和内容边界验证；
- 上传临时文件自动清理；
- AI 输入、输出、并发、超时和总预算边界；
- 日志脱敏，不记录密钥、完整对话敏感字段或原始表格内容；
- 数据库和 Blob 凭据只存在服务器部署配置中。

本次删除或不建设的高级部分包括：客户注册、多租户成员体系、客户级 RLS、Key Vault、自动密钥轮换、真实数据迁移、正式生产恢复演练和复杂的双环境发布治理。

## 12. 关键页面与流程

### 12.1 观众流程

```text
进入公开 URL
  → 建立或恢复 Demo 会话
  → 固定当前公共数据版本
  → 查看只读仪表盘/预测/利润/行动卡
  → 使用推荐问题或自由文本询问 AI
  → 模拟批准/调整/驳回
  → 刷新后继续，或主动结束 Demo
```

### 12.2 操作者流程

```text
操作者登录
  → 上传合成/脱敏 Excel 或 CSV
  → 识别、映射、标准化和质量检查
  → 原子提交为新数据版本
  → 查看分析和证据
  → 手动发布为公共 Demo 版本
  → 处理行动卡并导出人工任务
  → 记录结果复盘
```

## 13. 异常与恢复策略

| 场景 | 预期行为 |
|---|---|
| 导入中任一文件失败 | 整批回滚，不生成部分版本；显示可修正的问题摘要 |
| 重复提交同一批次 | 幂等返回原结果或阻止重复累计 |
| Blob 写入成功但数据库提交失败 | 清理未被引用的临时对象，不发布版本 |
| 发布新 Demo 版本失败 | 继续使用原公共版本 |
| 应用进程重启 | 从 PostgreSQL 恢复未过期会话和持久状态 |
| 观众刷新页面 | 恢复同一会话、数据版本、对话和模拟行动 |
| 会话过期 | 清理临时状态并引导开始新 Demo |
| AI 超时、供应商故障或预算达到上限 | 显示 AI 暂不可用，保留确定性功能 |
| API Key 无效 | 仅操作者看到可处理的配置状态；公共页不暴露密钥细节 |
| 某个观众发送并发请求 | 当前会话只保留一个在途请求，其余拒绝或排队 |

## 14. 测试与 Demo 验收

### 14.1 自动化测试

- 报表识别、字段映射和标准化单元测试；
- 多文件原子提交、回滚和幂等重放测试；
- 数据版本库、发布指针和回退测试；
- PostgreSQL/Alembic 迁移及重启读回测试；
- Blob 临时区清理、标准化产物引用和孤立对象处理测试；
- 观众刷新、空闲过期、绝对过期和主动结束测试；
- 观众之间 AI 对话和模拟行动隔离测试；
- 公共接口禁止上传、编辑和发布测试；
- 单一操作者登录、上传、提交、发布、持久化和导出测试；
- 固定问题集 AI 评估：数字引用、证据引用、不确定性、证据不足拒答；
- API Key 不进入客户端、日志、数据库和错误响应的检查；
- AI 故障时确定性功能继续可用的测试。

### 14.2 浏览器验收

- 桌面端和移动端观众主流程；
- 操作者登录、导入、发布和导出主流程；
- 刷新、关闭后重开、过期和重新开始 Demo；
- 发布新版本时，已有观众固定旧版本、新观众进入新版本；
- AI 对话和行动卡在不同观众之间互不可见；
- 页面明确标注演示数据和非真实操作。

### 14.3 容量基线

首发验收按同一时段 15 个观众会话执行基本并发验证，包括只读页面、AI 请求限流和会话恢复。若实际活动预计明显超过 15 人同时使用，必须在发布前重新确定容量、预算和验收负载，不能直接沿用本基线。

### 14.4 上线证据定义

只有同时具备以下证据，才可称为“Azure Demo 已验收”：

- Azure URL 可访问；
- PostgreSQL 和 Blob 使用部署后的实际配置；
- 数据库迁移完成；
- 观众与操作者浏览器主流程通过；
- 重启读回、会话恢复和发布版本固定行为通过；
- AI 固定问题集和不可用路径通过；
- 回滚到先前应用版本和先前公共数据版本的步骤已验证。

本地测试通过、代码合并、CI 通过或 URL 单纯可访问，均不能单独代表 Azure Demo 完成，更不能代表 Production readiness。

## 15. 交付阶段与预计工期

在范围固定、连续执行且所需外部授权当天完成的前提下：

| 交付点 | 预计时间 |
|---|---|
| 可用本地版本 | 约 3–4 周 |
| Azure 公开 Demo URL | 约 4–6 周 |
| 完整 Demo 验收与交付 | 约 5–7 周 |

建议阶段：

1. 第 1 周：核实现有 BP 可复用代码、数据库 schema、Blob 接口和测试证据。
2. 第 2–3 周：迁移导入/标准化/版本库，完成单操作者和公共预设数据路径。
3. 第 3–4 周：接入已批准的新品预测、利润归因和证据层；完成 AI 问答。
4. 第 4–5 周：完成行动卡、导出、结果复盘和浏览器主流程。
5. 第 5–7 周：Azure 部署、迁移、并发验证、重启恢复、回滚和最终 Demo 验收。

如果算法子规格、外部授权、Azure 资源或现有 BP 复用验证未按时完成，工期需要相应调整。

## 16. 实施约束与顺序

后续实施必须遵守以下顺序：

1. 先审计现有 BP 实现和测试，不按旧计划或界面假设功能已完成。
2. 优先复用已经验证的适配器、标准化、原子提交和数据版本库。
3. 先建立 PostgreSQL/Alembic/Blob 的持久化主干，再接观众会话和 AI。
4. 确定性计算和证据引用先于 AI 自然语言层。
5. 每个算法切片先批准子规格，再用测试驱动实现。
6. 先完成本地端到端，再部署 Azure；部署后重新执行实际环境验收。
7. 不修改或迁移现有 BP 的真实/历史数据；NEWCaostone 从合成演示数据开始。

## 17. 主要风险与控制

| 风险 | 控制方式 |
|---|---|
| 误把已有界面当成完整后端能力 | 以代码、数据库迁移和可运行测试逐项核实 |
| 多文件导入产生不一致数据 | 原子提交、回滚、幂等批次和版本化 |
| 发布新数据影响正在观看的人 | 会话进入时固定数据版本 |
| 单一 API Key 被滥用或费用失控 | 服务端 Key、单请求边界、会话并发、全局并发和部署预算上限 |
| AI 编造业务数字 | 确定性计算为权威，强制证据引用，证据不足拒答 |
| Demo 简化被误认为真实客户安全 | 页面和文档持续标注 Demo-only / non-Production |
| Azure URL 可用但持久化未完成 | 强制 PostgreSQL/Blob、重启读回和浏览器验收证据 |
| 算法定义不足导致返工 | 新品预测、利润归因和置信度分别建立子规格 |

## 18. 完成定义

本项目在以下条件全部满足时，才达到本设计的“完整 Demo 交付”：

- 单一操作者能导入合成/脱敏表格并原子提交为长期标准化数据版本；
- 原始上传文件按生命周期删除；
- 操作者能手动发布一个公共预设版本；
- 匿名观众不能上传或编辑数据，但能使用只读分析、AI 和临时行动卡；
- 不同观众的会话状态互相隔离，刷新可恢复，过期可清理；
- 新品预测和利润归因使用已批准且经过测试的确定性规格；
- AI 使用固定低消耗模型、一个临时服务端 Key，并提供数字、证据和限制；
- 完整行动卡以人工决策、文件导出和结果复盘为终点，不直接操作外部平台；
- PostgreSQL、Alembic、Blob 和 Azure 实际环境验收通过；
- 页面、文档和演示话术不声称真实客户使用或 Production readiness；
- 演示结束后撤销 AI API Key 并清除部署配置。
